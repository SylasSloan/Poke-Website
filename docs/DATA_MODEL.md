Data model — Pokémon Site

This document explains the shape of Pokémon records the app expects and the localStorage formats used.

Dataset files

There are three JSON files, generated in this order by the `python/`
pipeline (see `docs/DEVELOPMENT.md` for the full command sequence):

- `json/pokemon-full-data.json` — the canonical, fully-enriched source file
  every Python script reads and writes in place. Not fetched by the app at
  runtime; it's the "master" record.
- `json/pokemon-index.json` — a lean array containing only the fields below
  under "Index fields", derived from the full file by
  `python/split_pokemon_data.py`. This is what `index.html` fetches for the
  main grid, and what `pokemon-detail.html` fetches for its prev/next pager
  and evolution-chart family lookup (both of which need to scan every
  Pokémon, not just the one being viewed).
- `json/details/{id}.json` — one small file per Pokémon containing the
  fields below under "Detail-only fields", also produced by
  `split_pokemon_data.py`. `pokemon-detail.html` fetches exactly one of
  these (for the Pokémon being viewed) and merges it onto the index record.

This split exists because the main grid only ever reads a handful of fields
per Pokémon, while the detail page needs much more (Pokédex entries, sprite
galleries, full per-generation movesets, etc.) — shipping everything to
every page made the main grid's initial load unnecessarily large.

Pokémon record shape

The application is resilient to slightly different dataset shapes, but the expected fields for a Pokémon record are:

Index fields (`json/pokemon-index.json`, also present in `pokemon-full-data.json`):

- id: number or numeric string (e.g., 1 or "1") — unique identifier.
- name: string — Pokémon name (lowercase or mixed case, UI capitalizes where helpful).
- region: string — the generation or region name (e.g., "generation-i" or "Gen I"). The app uses canonicalized region names internally.
- sprite: string — URL path to a sprite image.
- types: array of strings — e.g., ["Grass","Poison"].
- abilities: array of strings — simple list of ability names.
- ability_details: optional array — objects containing { name, is_hidden, description } or nested shapes from PokeAPI. `description` is used by both the main grid (search-by-ability, the in-grid ability modal) and the detail page, so it stays in the index rather than moving to the per-Pokémon detail file.
- stats: object with numeric keys such as { hp, attack, defense, "special-attack", "special-defense", speed }.
- flavor_text: optional string for search.
- evolves_from: optional string — the preceding species name, used by the detail page to reconstruct evolution families across the whole index.
- evolution_trigger: optional object — condition(s) for evolving into this Pokémon (type, min_level, item, held_item, time_of_day, etc.), used to label evolution-chart arrows.

The app accepts datasets where some of these fields are missing and will gracefully omit UI parts.

Detail-only fields (`json/details/{id}.json`, also present in `pokemon-full-data.json`), consumed only by `pokemon-detail.html`:

- height, weight: numbers in decimetres/hectograms (PokeAPI units).
- base_experience, capture_rate, base_happiness, hatch_counter: numbers.
- genus: string (e.g., "Seed Pokémon").
- growth_rate: string.
- ev_yield: array of { stat, value }.
- egg_groups: array of strings.
- gender_rate: number (PokeAPI's eighths-female encoding, -1 = genderless).
- names: array of { language, name } — other-language names.
- pokedex_entries: array of { versions: string[], text } — deduplicated flavor text per game.
- sprites_by_gen: object keyed by generation, then game, of { normal, shiny } sprite URLs.
- moves_by_generation: array of { label, level_up, tm, hm, tutor, egg }, one entry per generation the Pokémon has learnset data for. `level_up` is an array of { level, label, name }; `tm`/`hm`/`tutor`/`egg` are arrays of move name strings. Generated by `python/enrich_moves_and_encounters.py`, which is also where the TM-vs-HM item lookup lives (PokeAPI's own move data only reports the learn method as "machine", not which kind).
- encounters_by_generation: array of { label, areas }, one entry per generation with wild-encounter data. `areas` is an array of { area, chips } where each chip is a formatted string like "Grass • Lv 3-5 • 45% • Time: Morning".

localStorage formats

- pokemonProgress (key: 'pokemonProgress')
  - JSON object keyed by region name:
    { "region-1": { seen: [1,2,3], caught: [2,3] }, "region-2": { ... } }
  - Stored via `StorageManager.saveProgress(progress)` which also caches the parsed value.

- selectedRegions (key: 'selectedRegions')
  - JSON array of region names, e.g. `["generation-i","generation-ii"]`.

- selectedTypesV1 (key: 'selectedTypesV1')
  - JSON array of lower-case type names, e.g. `["grass","poison"]`.

- pokemonFavoritesV1 (key: 'pokemonFavoritesV1')
  - JSON array of numeric Pokémon ids, e.g. `[1,25,150]`.

- typesPanelCollapsed (key: 'typesPanelCollapsed')
  - "1" or "0" string to indicate the persisted collapsed state of the left types panel.

Notes on robustness

- StorageManager caches parsed progress and exposes `invalidateProgress()` — callers that change storage outside StorageManager should call this method or use StorageManager.saveProgress to maintain cache coherence.
- Data imported from files should follow the same `pokemonProgress` shape. The import logic will validate the structure where possible.
